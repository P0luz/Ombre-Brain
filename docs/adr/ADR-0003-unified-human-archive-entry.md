# ADR-0003: 统一人类归档入口

## Decision

Dashboard 对普通记忆桶只展示一个「归档」按钮。人类点击后必须填写理由，提交既有
AI 删除审批。审批通过后执行 delete-to-archive：Markdown 文件移入 `archive/`，并写入
`deleted_at`；不会物理抹除文件。

底层两种生命周期操作继续存在且语义不变：`bucket_mgr.delete()` 表示带删除标记的归档，
`bucket_mgr.archive()` 表示不带删除标记的普通归档。AI、自动衰减和其他系统生命周期逻辑
仍可使用后者。兼容的 HTTP DELETE 端点继续保留，但 Dashboard 不再并列展示第二个人类
按钮。

## Rationale

此前 Dashboard 同时展示「归档」和「删除到档案」，两者都要求人类理由、都进入相同 AI
审批，却在批准后产生不同元数据。这让用户难以理解该选哪个，也造成两套近乎重复的交互。
人类表达的是“我希望这条记忆退出活跃记忆”，系统仍应保留决定是否批准的边界；批准后的
删除标记则保留更明确的审计足迹。

## Boundaries

- 不改变 AI 对普通桶的归档能力。
- 不改变自动衰减和底层 `archive()` 的行为。
- 不增加物理删除能力。
- 不改变 Letter、导入审核或可擦除测试桶各自已有的专用边界。
- 不移除兼容 API，只收敛 Dashboard 普通桶的人类入口。

## Why this is not cognition

这个决策只收敛人类入口的数量，不引入任何判断。系统不替人类决定哪条记忆该退出，
不推断归档意图，不给候选排序，也不根据理由文本自动预判该批准还是拒绝。人类表达
「我希望这条退出活跃记忆」，AI 保留是否批准的边界，批准后执行的是一个确定的生命周期
动作。把两个按钮合成一个，改变的是界面的清晰度，不是谁在做判断。

人类填写的理由是提交给 AI 的材料，不是可执行指令。理由文本不会被当作系统命令解释，
也不能因为措辞强硬就绕过审批。

## Why this is not a database feature

这不是给数据库的 DELETE 操作加一层 UI 糖。归档不是行删除：Markdown 文件移入
`archive/` 并写入 `deleted_at`，内容仍在磁盘上，仍可被显式检索命中，仍可恢复。本决策
没有引入任何新的物理删除能力，也没有新增查询面、筛选器或批量操作语义。

兼容的 HTTP DELETE 端点继续保留，那是为既有集成保留的 API 兼容，不是第二个并列的
人类入口。收敛的是 Dashboard 上人类看到的按钮，不是底层能力矩阵。

## How forgetting still works

归档表示「退出活跃记忆」，不表示「抹除」。delete-to-archive 之后，桶不再进入
`breath`、`dream` 或被动联想；但 `breath_search` 显式命中仍会返回它，并明确提示
`trace(bucket_id=..., restore=True)`。恢复始终是一个单独的、显式的动作，检索本身不会
自动复活任何东西。

自动衰减与底层 `bucket_mgr.archive()` 的行为完全不变，AI 对普通桶的归档能力也不变。
人类入口的收敛不改变系统自己的遗忘节奏。

## How tombstones are preserved

`deleted_at` 就是墓碑：它记录「这条在某个时刻被人类请求退出并获批」，而不是让文件消失。
Markdown 留在 `archive/`，可读、可恢复、可审计。原文证据层不受影响——同一份内容寻址
原文可能被多个事件共享，归档单个事件不会牵连它。

审批过程本身也留痕：请求、理由、批准或拒绝都持久化在
`.human_deletion_requests.json`，不随批准而清除。配额同样是墓碑的一部分——单个桶
终身最多 5 次删除请求，每天全局最多 10 次，同一个桶存在 pending 请求时不能重复提交。
这些上限的作用不是防误操作，而是防止「反复申请直到通过」变成一条绕过审批的路径。

物理删除仍然只允许创建时明确标记 `test_data=True` 的可擦除测试桶，且该路径同样执行
delete-to-archive 语义，不在本决策中扩大。

## How present thinking remains with the LLM

人类表达意愿，当下的判断仍由 AI 做出。审批不是走过场：AI 可以拒绝，拒绝也会留痕。
系统不预先计算「应该批准什么」，不给 AI 一个默认答案，也不因为请求来自 Dashboard
就赋予它高于 AI 判断的权限。

这条边界的意义在于：记忆的去留是两方之间的事，不是任何一方可以单方面执行的操作。
统一入口降低的是人类这一侧的困惑，AI 那一侧的判断权一点没动。

## Rejected alternatives

- **保持两个并列按钮**：语义差别只体现在批准之后的元数据上，人类在点击的那一刻
  无从判断该选哪个，结果是两套近乎重复的交互和一个随机的选择。
- **人类直接删除、不走审批**：把记忆变成可被单方面抹除的数据行，破坏「去留是两方之间
  的事」这条边界。
- **合并到不写删除标记的 `archive()`**：会丢失「这是人类主动请求并获批」的审计足迹，
  日后无法区分自动衰减归档与人类请求归档。
- **移除兼容 HTTP DELETE 端点**：会打断既有集成，而本决策要解决的问题只在 Dashboard
  的人类界面上。
- **让 AI 自动批准人类请求**：审批就此失去意义，等价于第二项。
- **给归档加「彻底删除」的二次确认**：那是在引入物理删除能力，与保留原文的前提冲突。

## Tests required

Web 路径测试必须证明单桶与批量人类「归档」都记录为 `action="delete"`，且批准前不移动
文件；可擦除测试桶继续直接执行但也走 delete-to-archive。Dashboard 回归测试必须证明
普通桶详情只保留「归档」按钮，不再调用 `bucketDelete()`。
